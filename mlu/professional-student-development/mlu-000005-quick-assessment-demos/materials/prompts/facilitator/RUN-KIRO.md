## Before the session — about 20 minutes

### 1. Open the workspace

In the Kiro window you have open: **Open a project** → choose

```
/Users/thook/dev/2026/mlu-symposium/kiro-grader
```

The Explorer should show `data/` with the four papers inside.

### 2. Generate `requirements.md`

Open Kiro's chat and paste this. **Then stop and read what comes back** — that pause is the
thing you are teaching.

```text
I want to build a grading assistant for a university course. Before any code, write
requirements.md.

It grades short student papers against a rubric in the "mlu-rubric/1" JSON format — see
data/rubric.json — where each criterion has an id, name, weight, description, present_when, and
levels "0" through "4", plus max_tier and grade_bands. It reads data/course-reading.pdf, which
defines what "correct" means for this assignment; data/roster.csv, the enrolled students; and
the papers in data/papers/. It produces draft grades for an instructor to review.

Write the requirements in EARS form — WHEN <trigger>, THE SYSTEM SHALL <response>. Cover at
minimum: reading and validating the rubric, choosing a tier per criterion, computing the
weighted grade, handling a roster student who submitted no paper, and presenting results to the
instructor.

Include exactly one requirement that uses an evaluative word with no defined pass or fail. Write
"WHEN a paper is submitted, THE SYSTEM SHALL grade it fairly" as its own requirement and leave it
in. I am using it in a workshop to show what an untestable requirement looks like. Do not flag
it, do not fix it, and do not add a note about it. Leave it sitting there looking reasonable.

Stop after requirements.md. Do not write design or tasks yet.
```

**Check before you move on — this is the segment's spine.** `requirements.md` must contain both
of slide 17's requirements, in words close to these:

> ① WHEN a roster student has no paper, THE SYSTEM SHALL flag them **missing** and SHALL NOT
> score them.
>
> ② WHEN a paper is submitted, THE SYSTEM SHALL grade it **fairly**.

If Kiro "helpfully" fixed ② or annotated it, tell it to restore the plain wording. **You need
that flaw intact.** It is the poll, and the poll is the segment.

### 3. Approve, then generate the design

```text
Approved. Now write design.md. Three decisions must be explicit in it, with the reasoning:

1. The model picks a tier from 0 to 4 per criterion. The weighted grade is CALCULATED in code
   from tiers and weights — never generated by the model, never adjusted by it. Grades must be
   exactly reproducible: the same paper and rubric produce the same number every time. Say in
   the design why: models are unreliable at arithmetic, and a grade is a record.

2. "Correct" means correct according to data/course-reading.pdf, not the model's general
   knowledge. Claims that contradict the reading are quoted alongside the passage that
   contradicts them.

3. Every student on the roster is accounted for. A student with no paper is reported as MISSING,
   never as a zero and never silently omitted.

Then stop, and wait for approval before writing tasks.
```

### 4. Approve, build, and run it once

```text
Approved. Now write the task list, then work through it. When it is built, run it over all four
papers in data/papers/ against data/rubric.json and data/roster.csv, and save the results.
```

**Then check the output — these are what slide 19 shows:**

- [ ] **Marcus Lee — F**, with his wrong running-time claims quoted against the reading
- [ ] **Diego Alvarez — MISSING**, not a zero, not skipped
- [ ] Aisha high, Priya very low, Leila around half
- [ ] Run it a second time: **the same numbers**. If they move, the model is doing the arithmetic
      and design decision 1 was not implemented.

Keep the results on screen in a tab, or screenshot them. That is your slide 19.

### 5. Leave these open, in this order

1. `requirements.md` — **this is what slide 17 projects**
2. `design.md` — scrolled to the three decisions
3. The saved results — slide 19

Zoom the editor font up. `requirements.md` has to be readable from the back of the Ballroom:
**Cmd-+** a few times, or Settings → `editor.fontSize` around 18–20.

## On stage — 13 minutes

### Slide 16 — Section *(~30 seconds)*

> "Third tool, built in Kiro. A grader is the tool where being wrong costs the most, so it is
> the one we built most carefully."

### Slide 17 — Review the spec before the code *(4 min)*

**Do:** Switch to Kiro. Project `requirements.md`.

**Say:**

- "In Quick — what you just did twice — you describe an app and fix it after you see it. In Kiro
  you approve the requirements, then the design, then the task list. Only then is any code
  written."
- **Poll the room:** *"Two requirements on the screen. Which one can't you test?"* **Take answers
  before giving the answer.**
- **The answer is ②.** "'Fairly' has no pass or fail. What would fair mean? The same paper gets
  the same score twice? Scores don't change with the student's name? Each of those *is* testable.
  'Fairly' isn't."
- Land the cost: "Fixing it now costs a sentence. Fixing it after the code exists costs a
  rebuild. Fixing it after it has graded two hundred papers costs a great deal more."

### Slide 18 — Three design decisions *(2 min)*

Scroll `design.md` and walk them:

1. **The math is in code.** "The model picks a 0–4 tier per criterion. The weighted grade is
   calculated, never generated — models are unreliable at arithmetic, and a grade has to be
   exactly reproducible."
2. **Correct means correct per the reading.** "This is why Marcus fails. His claims are checked
   against the course reading, not the model's general sense of the topic."
3. **Everyone is accounted for.** "Diego shows up as missing, not as a silent zero."

**The line:** *"The model judges. The code counts. The instructor decides."*

### Slide 19 — Five students, one rubric *(3 min)*

**Do:** Show the saved results. Say plainly that you ran it this morning — nobody minds, and it
buys you the three minutes.

- **Marcus — F**, with his wrong claims quoted back as evidence.
- **Diego — missing.** "It doesn't hand him a zero. It asks you to confirm."
- "Every one of these is a draft. The instructor reads them, adjusts them, and only then records
  anything."
- **Leila, about half.** "And Leila hadn't finished. What if she'd found that out *before* the
  deadline?"

## If it goes wrong

| | |
|---|---|
| **Kiro won't run / credits gone** | The segment works from the artifacts alone. Project `requirements.md`, run the poll, walk the three decisions, show the saved results. Say you are showing a build from this morning. **Nothing is lost** — the approval sequence is the content, and it needs no software. |
| **Kiro removed the "fairly" requirement** | Say it yourself: write both requirements on a slide-free screen, or read them out. The poll works spoken. |
| **A CS faculty member answers instantly** | Good. Ask them *why*, then make it general: "Right — and that's a whole class of words. Effective. Appropriate. Robust. User-friendly." |
| **Running long at 0:57** | Cut slide 19 to Marcus and Diego only. Do not cut the slide 17 poll; it is the best two minutes in the segment. |

> **Do not turn this into a demo of a different grading app.** The teaching content is the
> approval sequence, not the grader. If you find yourself explaining features, you have lost the
> thread — go back to "which one can't you test?"

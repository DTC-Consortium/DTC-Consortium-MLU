# PROMPT F2 — The Grading Assistant, in Kiro *(facilitator only)*

**Slides 16–19 · 13 minutes · the room watches, nobody builds**

Kiro is not on anybody's machine. This segment is a demonstration, and its content is not the
grader — it is **the difference between the two ways of building**.

- In **Quick**, and in the three prompts the attendees just used: you describe an app, you get
  one, and you fix what is wrong after you see it.
- In **Kiro**: you approve the **requirements**, then the **design**, then the **task list**, and
  only then is any code written.

For a tool that assigns grades, that difference is the argument. Slide 17 exists so the room can
find an untestable requirement *before* it becomes code.

---

## What you must have ready to project

1. **`requirements.md`, open in Kiro**, containing the two requirements on slide 17 — one
   testable, one deliberately not. The room's job is to spot which. Keep the untestable one.
2. **The grader already run once, with results saved**, in case the live run is slow.
3. The design and task documents Kiro generated, ready to scroll.

---

## Step 1 — the spec, in Kiro

Paste this as the opening prompt in a new Kiro project. Then **stop at the requirements stage**
and read what it produced before approving anything — that pause is the thing you are teaching.

```text
I want to build a grading assistant for a university course. Before any code, write
requirements.md.

It should grade short student papers against a rubric supplied in the "mlu-rubric/1" JSON
format: a criteria array where each criterion has an id, name, weight, description,
present_when, and levels "0" through "4", plus max_tier and grade_bands. It reads a course
reading PDF that defines what "correct" means for this assignment, a roster CSV of enrolled
students, and a folder of student papers. It produces draft grades for an instructor to review.

Write the requirements in EARS form — WHEN <trigger>, THE SYSTEM SHALL <response>. Cover at
minimum: reading and validating the rubric, choosing a tier per criterion, computing the
weighted grade, handling a student on the roster who submitted no paper, and presenting results
to the instructor.

Include exactly one requirement that uses an evaluative word with no defined pass or fail —
write "THE SYSTEM SHALL grade it fairly" as its own requirement and leave it in. I am using it
in a workshop to show what an untestable requirement looks like. Do not flag it, do not fix it,
and do not add a note about it. Leave it sitting there looking reasonable.

Stop after requirements.md. Do not write design or tasks yet.
```

**Check before you move on:** `requirements.md` contains both slide 17 requirements —

> ① WHEN a roster student has no paper, THE system SHALL flag them **missing** and SHALL NOT
> score them.
> ② WHEN a paper is submitted, THE system SHALL grade it **fairly**.

If Kiro "helpfully" fixed ② or annotated it, tell it to restore the plain wording. **You need
that flaw intact** — it is the slide-17 poll, and the poll is the segment.

---

## Step 2 — the design

Approve the requirements, then prompt:

```text
Approved. Now write design.md. Three decisions must be explicit in it, with the reasoning:

1. The model picks a tier from 0 to 4 per criterion. The weighted grade is CALCULATED in code
   from tiers and weights — never generated by the model, never adjusted by it. Grades must be
   exactly reproducible: the same paper and rubric produce the same number every time. Say in
   the design why: models are unreliable at arithmetic, and a grade is a record.

2. "Correct" means correct according to the uploaded course reading, not the model's general
   knowledge. Claims that contradict the reading are quoted alongside the passage that
   contradicts them.

3. Every student on the roster is accounted for. A student with no paper is reported as
   MISSING, never as a zero and never silently omitted.

Then stop, and wait for approval before writing tasks.
```

## Step 3 — the tasks

```text
Approved. Now write the task list, then work through it.
```

## How to run the segment

**Slide 17 — 4 minutes.** Project `requirements.md`. Make the contrast explicit: *"In Quick you
describe it and fix it after. Here you approve the requirements, then the design, then the tasks —
and only then does code exist."* Then poll: **"Two requirements. Which one can't you test?"**

Take answers before giving the answer. It is **②**. *"Fairly" has no pass or fail. What would
fair mean? The same paper gets the same score twice? Scores don't change with the student's
name? Each of those* is *testable. "Fairly" isn't.*

Land the cost: *"Fixing it now costs a sentence. Fixing it after the code exists costs a rebuild.
Fixing it after it has graded 200 papers costs much more."*

**Slide 18 — 2 minutes.** The three decisions, then the line: **"The model judges. The code
counts. The instructor decides."**

**Slide 19 — 3 minutes.** Run the grader on all five, or show the saved results. Marcus **F**,
with his wrong claims quoted back. Diego **missing** — *"it doesn't hand him a zero, it asks you
to confirm."* Leila 50% — *"and Leila hadn't finished. What if she'd found that out* before *the
deadline?"* That question is the next tool.
